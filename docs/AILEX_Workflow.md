**AILEX — Памятка по рабочему циклу**

*Как мы вносим правки в код и обновляем приложение*

# 0. Инструкция для нового чата (читать первым делом)

При каждом новом чате Claude должен первым делом прочитать документацию проекта с GitHub. Без этого Claude работает вслепую и может предложить то, что уже реализовано.

**Команды для чтения документов в начале сессии:**

```
# 1) Текущее состояние — читать первым. Заодно отсюда берём имя актуальной спеки.
curl -s https://raw.githubusercontent.com/4wood70/ailex/main/docs/AILEX_Status.md -o /tmp/ailex_status.md
cat /tmp/ailex_status.md

# 2) Последняя спецификация. Имя версионируется (AILEX_4_19 → 4_22 → …), поэтому НЕ хардкодим:
#    Status в шапке несёт строку «Текущая спецификация: docs/AILEX_X_XX.md» — читаем её оттуда.
#    (Сознательно НЕ используем GitHub API /contents — у него лимит 60 запросов/час на общий IP, падает с 403.)
SPEC=$(grep -oP 'Текущая спецификация: docs/\KAILEX_\d+_\d+\.md' /tmp/ailex_status.md)
echo "Читаю спеку: $SPEC"          # пусто — НЕ гадать, см. «Какая спека актуальна» ниже
curl -s "https://raw.githubusercontent.com/4wood70/ailex/main/docs/${SPEC}"

# 3) Глоссарий и принятые решения
curl -s https://raw.githubusercontent.com/4wood70/ailex/main/docs/AILEX_Glossary.md
```

Порядок чтения: сначала `AILEX_Status.md` (текущее состояние + указатель спеки), затем спека и глоссарий по необходимости.

**Какая спека актуальна — решает ТОЛЬКО указатель в Status.** Строка «Текущая спецификация: docs/AILEX_X_XX.md» обновляется при каждом подъёме версии спеки (раздел 9) и всегда ведёт на свежий файл.

- **Старые спеки, лежащие рядом, не читать НИКОГДА** — ни в git, ни в локальной папке, сколько бы их там ни накопилось. Уборка — дело наживное: когда коммитит Claude, старая спека удаляется тем же коммитом; когда Константин — он удаляет её, когда доходят руки, и рядом могут лежать две-три. Сама по себе старая спека не ошибка и не повод что-то чинить.
- **Номер в имени файла ни о чём не говорит.** Больший номер — не признак актуальности: файл мог остаться от сборки, которую откатили. Верен тот файл, который назван в Status, и только он.
- **Указателя нет или файл по нему не открывается** — остановиться и спросить Константина. Не подставлять «похожее» имя, не брать файл с наибольшим номером, не гадать: работа по устаревшей спеке хуже, чем пауза на один вопрос. Страховочного имени в команде намеренно НЕТ — жёстко вписанное имя устаревает и однажды тихо уводит сессию на старый документ.

**Лишние спеки — сказать один раз и работать дальше.** Если рядом видны спеки, кроме названной в Status, Claude один раз перечисляет их по именам («лежат AILEX_4_101.md и AILEX_4_102.md, актуальна 4_103 — удалить можно когда удобно») и больше к этому не возвращается. Это уборка, а не препятствие: на работу лишние файлы не влияют.

**Важно:** сам `AILEX_Workflow.md` (этот файл) подгружается в контекст автоматически из документов проекта Claude — отдельной `curl`-командой его читать НЕ нужно. Копия лежит и в репозитории (`docs/AILEX_Workflow.md`); при правке обновляются ОБЕ — сначала документ проекта, затем файл в репозитории (раздел 11).

Если Constantin говорит «прочитай документацию» или «освежи контекст» — выполнить эти три команды (Status → последняя спека → глоссарий).

**Выкладка — коммит прямо в GitHub (с 08.11.2026).** Если у сессии есть доступ на запись к `4wood70/ailex`, Claude сам делает commit и push в `main`. В локальную папку `X:\GD\Ailex\ailex` Claude НЕ пишет: её Константин синхронизирует сам через GitHub Desktop (Pull). Claude напоминает о Pull после каждого пуша и, если сессия связана с компьютером, проверяет в начале сессии, не отстаёт ли локальная копия. Порядок — раздел 11.

**Сверка даты проверки моделей Gemini (при каждом чтении Status).** В шапке `AILEX_Status.md` есть строка «Последняя проверка моделей Gemini: ДД.ММ.ГГГГ». Прочитав Status, Claude сравнивает эту дату с текущей:
- прошло больше месяца → сказать об этом Constantin'у **первым же ответом сессии** и предложить проверку по разделу 10;
- меньше месяца → молчать, ничего не предлагать.

Смысл: раздел 10 предписывает проверять «планово раз в 1-2 месяца», но у Claude нет памяти между сессиями, и без опоры на дату в документе «планово» не наступает никогда. Проверка держится с двух сторон: Constantin приносит новости о версиях Gemini, когда они до него доходят; Claude не даёт сроку уползти незаметно. Решение, что делать с новой моделью, в обоих случаях принимает Constantin.

**Текущий билд:** проверять через:
```
curl -s https://raw.githubusercontent.com/4wood70/ailex/main/index.html | grep APP_VERSION
```

# 1. Структура репозитория

```
4wood70/ailex/
├── index.html          — основное приложение (вся логика, UI)
├── sw.js               — сервис-воркер (версионирование кэша)
├── manifest.webmanifest
├── icons/
└── docs/
    ├── AILEX_4_NN.md   — методическая конституция (спецификация); имя версионируется,
    │                     имя актуальной берётся из указателя в Status, а не отсюда
    ├── AILEX_Status.md — текущий статус, очередь задач
    ├── AILEX_Glossary.md — глоссарий и принятые решения
    └── AILEX_Workflow.md — этот файл (копия документа проекта Claude)
```

В `docs/` должна оставаться ровно ОДНА спецификация — та, на которую указывает Status: предыдущая удаляется тем же коммитом, что добавляет новую, история при этом сохраняется в git.

Но это порядок, а не условие работы. Фактически рядом могут лежать несколько старых спек (например, если коммит делал Константин и удаление отложено). Новая сессия от этого не страдает: актуальную спеку определяет указатель в Status, а не содержимое папки (раздел 0).

`AILEX_Workflow.md` живёт в двух местах: основной экземпляр — в документах проекта Claude (подгружается в контекст сам), копия — в `docs/`. Правятся обе.

# 2. Нумерация версий

Два независимых счётчика:

**Билд** (`v35`, `v36`...) — поднимается при каждом коммите в GitHub. Прописывается в `APP_VERSION` (index.html) и `CACHE` (sw.js) — всегда совпадают. Проставляет Claude автоматически.

**Спецификация** (`4.19`, `4.20`...) — поднимается только при содержательном изменении: новая функция, изменение методики, новый контракт с Gemini, архитектурное решение. Мелкий багфикс или косметика — не повод. Название файла `AILEX_X_XX.md` всегда совпадает с последней записью в истории версий внутри документа.

| Что изменилось | Билд | Спецификация |
|---|---|---|
| Любой коммит (багфикс, косметика) | +1 | не меняется |
| Новая функция / методика / контракт | +1 | +0.1 |

# 3. Роли (кто что делает)

- **Claude** — готовит код: пишет/правит файлы целиком, сам проставляет номер билда. Код вручную не читается и не редактируется.
- **Claude делает commit и push в GitHub сам**, если у сессии есть доступ на запись к репозиторию (решение Константина 08.11.2026). Старую спеку удаляет тем же коммитом.
- **Constantin** синхронизирует локальную папку `X:\GD\Ailex\ailex` через GitHub Desktop (Fetch → Pull). В локальную папку Claude не пишет — иначе Desktop видит «изменения» и Pull не проходит (случай v160).
- **Нет доступа на запись** — запасной порядок раздела 11: файлы отдаёт Claude, commit и push делает Константин.

# 4. Полный цикл одной правки

1. **Обсуждаем.** Constantin говорит что нужно изменить. Решаем вместе как именно.
2. **Обновляем спецификацию** (если изменение содержательное). Claude готовит обновлённый `AILEX_X_XX.md` и `AILEX_Status.md`.
3. **Claude готовит файлы.** Получаете целиком готовые `index.html` и/или `sw.js` с поднятым билдом. Документы — если нужно.
4. **Commit и push.** Есть доступ на запись — Claude коммитит и пушит в `main` сам (раздел 11), сообщение коммита показывает в чате. Нет доступа — запасной порядок раздела 11.
5. **Сверяемся.** Claude заново клонирует репозиторий и побайтно сверяет файлы с собранными.
6. **Локальная папка.** Константин делает Pull в GitHub Desktop.

# 6. Сообщения коммитов (GitHub Desktop)

**Где выдаётся коммит-сообщение:** когда Claude коммитит сам — это сообщение его коммита, и в чат оно выводится для сведения. Когда коммитит Константин — Claude выдаёт готовое сообщение **прямо в чат, отдельным блоком кода для копирования**. В обоих случаях — НЕ вписывает его в этот документ и не хранит примеры коммитов здесь. Документ описывает только формат; конкретные сообщения живут в чате той сессии, где сделан билд.

**Язык:** сообщения коммитов пишутся **строго на английском языке**.

**Формат** — два поля, Summary и Description. Claude выдаёт их в чате одним блоком вида:

```
vNN: short imperative summary of the change

- bullet describing change 1
- bullet describing change 2
- rationale where it matters
```

Правила содержания:
- Summary — одна строка, начинается с номера билда (`vNN:`), повелительное наклонение, по сути изменения.
- Description — маркированный список конкретных правок; где важно — краткое обоснование (почему так, а не иначе).
- Для чисто документальных коммитов summary вида `docs: update Workflow and Status` (без номера билда).

# 7. Три железных правила

**Правило 1. После каждого коммита — проверить билд.**
Claude читает `APP_VERSION` с GitHub и сравнивает с тем что было отправлено.

**Правило 2. Билд поднимаем всегда — даже для крошечной правки.**
`APP_VERSION` в index.html и `CACHE` в sw.js должны совпадать (например `v35` и `ailex-v35`). Без этого у пользователей залипает старый кэш PWA.

**Правило 3. Перед выдачей файлов — три проверки, все обязательны.**
1. Синтаксис скрипта (`node --check`).
2. **Весь скрипт — на необъявленные имена** (eslint, правило `no-undef`). Введено в v155: правка v153 перенесла из квеста вызов с именем `sc`, которого в задании «собери фразу» нет, и верный ответ ронял приложение. Синтаксически такой код верен, падает он только при исполнении той строки — ни синтаксис, ни прогон до меню этого не видят. Та же проверка нашла две тихие поломки, жившие много билдов.
3. **Прогон в настоящем DOM** (jsdom): запуск → экран профилей → вход в профиль → главное меню, плюс задание «собери фразу» до конца с вводом ответа и нажатием «Проверить». Ошибок — ноль.

Если правка касается экрана, до которого прогон не доходит, — дописать прогон до него, а не выдавать вслепую.

# 8. Если что-то пошло не так

- Claude видит старый код → попросить прочитать файл заново с GitHub (команды из раздела 0).
- Обновление не видно в приложении → проверить что билд поднят и коммит прошёл.
- Не уверены какая версия в репозитории → `curl` на `APP_VERSION` (см. раздел 5).

# 9. Завершение сессии — обязательный шаг

**После того как готовые файлы выданы Constantin'у, но ДО закрытия чата:**

Если в сессии были содержательные изменения (новые функции, багфиксы, архитектурные решения) — Claude обязан подготовить обновлённый `AILEX_Status.md` и предложить его Constantin'у.

**Что включать в обновление Status:**
- Все реализованные в этой сессии изменения — добавить в раздел 1 с указанием билда.
- Очередь задач (раздел 7) — очистить то, что реализовано.
- Текущий фокус (раздел 6) — обновить.
- Дата последнего обновления — проставить текущую.
- Указатель спеки в шапке («Текущая спецификация: docs/AILEX_X_XX.md») — обновить, если в сессии поднималась версия спеки. Это ЕДИНСТВЕННЫЙ ориентир: раздел 0 читает имя актуальной спеки только отсюда, и если строка не обновлена, следующая сессия будет работать по старому документу, даже когда новый лежит рядом. Поднял версию спеки — в том же действии поправь строку.

**Регулярная очистка списка приоритетов (обязательно каждую сессию):** раздел 7 (очередь) и раздел 6 (фокус) — это списки ТОЛЬКО актуального. Любой пункт, реализованный в коде, в ту же сессию убирается из развёрнутого вида: его место — короткая строка-сводка («QUEUE-NN — закрыт в vN, детали в разделе 1»), а полное описание уже живёт в разделе 1 (по билдам) и в истории git. Накапливать закрытые пункты в очереди запрещено — раздутый список заставляет следующую сессию тратить внимание на разбор давно сделанного и повышает риск предложить как новое то, что уже есть. Принцип: в разделах 6 и 7 не должно оставаться ни одного пункта, который полностью закрыт кодом. Пункты «mitigated подсказками» (сознательно без кода) и «проверить на тесте» (код не требуется) — это НЕ закрытые, их оставляем в свёрнутом виде с пометкой статуса.

**Почему это важно:** Claude не имеет памяти между сессиями и полностью опирается на документы. Если Status не обновлён после сессии — следующий чат начнётся с устаревшей картиной мира и может предложить то, что уже сделано, или потерять контекст принятых решений.

**Триггер для Constantin'а:** если в конце сессии Claude не предложил обновить документы — напомни: «обнови статус».

**Проверка соседних чатов:** если Constantin говорит что несколько последних сессий не документировались — Claude должен прочитать последние чаты проекта через инструмент `recent_chats` и восстановить пропущенные изменения в Status перед продолжением работы.

# 10. Проверка моделей Gemini (периодически)

Список моделей в `index.html` (`Gemini.MODELS`, искать по `MODELS:` — номер строки плывёт от билда к билду) захардкожен сознательно — это модели, которым мы доверяем методику. Google периодически выкатывает новые flash и отключает старые. Автоподхват новейших отклонён (v44 + обсуждение v57): эндпоинт ListModels не отдаёт лимиты, «новее» ≠ «лучше для нас», новая модель может тихо сдвинуть методику (а конституция требует: смена версии Gemini не меняет методику). Поэтому проверка — ручная, по триггеру, человек в цикле.

**Когда проверять:**
- Загрузка приложения стала медленной (10+ сек) — первый признак мёртвой модели в списке (симптом v44: залипший дохлый эндпоинт).
- Планово раз в ~1–2 месяца — отсчитывается от строки «Последняя проверка моделей Gemini» в шапке Status, сверку делает Claude в начале сессии (раздел 0).
- Когда Constantin узнал о новой версии Gemini flash (письмо Google, новость) — приносит в чат.
- Когда Claude встретил упоминание новой модели в ходе работы — сообщает Constantin'у, решение за ним.

**Проверка остаётся у нас, в приложение её не выносим.** Детектор новых моделей внутри приложения (периодический ListModels, пометка мёртвых, флажок «доступна новая модель» в Настройках) обсуждался и отклонён 16.08.2026: конечному пользователю такие сообщения непонятны и не нужны, а решение «доверяем ли мы этой модели методику» всё равно принимает Constantin. Пользователь не должен участвовать в наших тестах.

**После проверки — обновить дату** в шапке `AILEX_Status.md` (строка «Последняя проверка моделей Gemini»), даже если ничего не изменилось: сам факт проверки и есть результат.

**Что живо у ключа:**
```
curl -s "https://generativelanguage.googleapis.com/v1beta/models?key=ВАШ_КЛЮЧ" | grep '"name"'
```
Возвращает модели, реально доступные ключу сейчас. Если модель из нашего `MODELS` тут не появляется — она мёртвая, убрать из кода.

**Лимиты API НЕ отдаёт** — RPM / TPM / RPD смотреть вручную в документации Google (страница Rate limits / Pricing, Free Tier). Порядок перебора в `MODELS` построен на RPM (щедрые лимиты — первыми; узкое место — именно RPM, не объём токенов), поэтому лимиты новой модели надо узнать ДО добавления.

**Что делать по итогу:**
- Мёртвую модель — удалить из `MODELS`, поднять билд (иначе залипший эндпоинт → медленная загрузка).
- Новую flash — НЕ добавлять автоматически. Принести в чат, обсудить, прогнать тест (держит ли строгий JSON-контракт, не поехала ли методика/тон), и только тогда добавить в `MODELS` на позицию по её RPM. Поднять билд.
- Модель с известным EOL удалять заранее, не дожидаясь даты отключения: фолбэк на модель, которая вот-вот умрёт, даёт тот же симптом v44. Так снят `gemini-2.5-flash` (EOL окт.2026) в билде v113.
- Отдельно проверять `thinkingConfig`: с v160 приложение шлёт `thinkingLevel: 'minimal'` (прежде `thinkingBudget: 0`), `temperature` не шлёт. Если модель отказывает в параметре мышления (400 с упоминанием thinking) — код сам переводит её на умолчание до конца сеанса; в консоли будет «не принял thinkingLevel». Заявленное Google качество новых моделей обычно меряется на уровне medium/high — к нашему minimal рекламные сравнения не относятся.
